# Carbide 请求边界压缩复测

日期：2026-10-09。沿用历史实验的 8 阶段、每阶段 56,000 字符、
100,000 Token 压缩预算和 2 组配对重复，使用当前配置的 `gpt-5.6-luna`。

修复后，相同工作负载参数下的累计请求计数减少 **44.440%**。
历史版本记录的是 **35.646%**。两个实验并非同一天运行，新增 Snip 工具
也改变了少量固定前缀，所以这是同参数复测，不是固定所有外部条件的因果实验。

| 指标 | 开启压缩 | 关闭压缩 |
| --- | ---: | ---: |
| 配对重复 | 2 | 2 |
| 每次模型请求 | 16 | 16 |
| 累计 count_tokens 返回值，均值 | 505,508 | 909,848 |
| 峰值单次 count_tokens 返回值 | 71,001 | 113,309 |
| 流式 Usage 总输入，均值 | 536,244.5 | 910,212 |
| 完成标记校验 | 2/2 | 2/2 |
| 实际触发层 | L1 | 无 |

主口径：`(909848 - 505508) / 909848 = 44.440%`。
流式 Usage 口径：`(910212 - 536244.5) / 910212 = 41.086%`。
峰值请求计数减少 37.339%。

## 为什么改善

之前仅在顶层用户请求开始时检查预算。第六阶段产生大工具结果后，
这一轮的下一次模型请求仍携带完整结果，直到第七阶段才执行 L1。

现在在每次模型调用前检查预算，包括同一个用户任务中的工具循环。
两组实验都在第六阶段的工具结果返回之后执行 L1，减少了随后模型请求的输入。
这项改动同时覆盖了 CLI 中只有一个用户请求、内部多次工具调用的长任务。

## 计量与边界

- 主口径直接调用真实 Provider 的 count_tokens 接口；失败时终止计量，
  不使用本地估算冒充 API 计数。两组 A/B 的工具 schema 均包含 Snip，
  关闭压缩组的 Snip 队列不修改历史。
- count_tokens 返回值与流式 Usage 并不完全一致。因此分别报告，
  不将 44.440% 直接解释为真实账单节省率。
- 缓存读取也属于模型输入。压缩会改变历史前缀，这次开启压缩组的
  平均未缓存输入为 90,292.5，关闭组为 31,620；需要结合中转的实际定价看费用。
- 这个八阶段任务仍以固定完成标记校验，只验证 L1 的计量轨迹。
  更严格的跨阶段字段保留、代码运行与 L2/L3/L4/恢复验证见
  [分层长会话报告](CONTEXT_COMPRESSION_LAYERED_EXPERIMENT.md)。
- 两组样本不足以支持延迟 SLA、通用成功率或任意任务的节省比例。
