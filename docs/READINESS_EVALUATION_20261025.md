# Carbide 实测报告：运行时可靠性与真实编码任务

评测日期：2026-10-25。目标是给项目经历补充可追溯证据，并找出能力边界，而非用通过率替代生产验收。

## 1. 实验范围与判定标准

本轮新增评测入口，不改动 Agent、Todo、Mailbox 或上下文压缩的业务实现。保留原工作区中的全部既有修改。

三类结果分开统计：

1. **组件可靠性**：真实 SQLite、操作系统进程、Git Worktree，配合确定性 Provider 注入故障；不消耗 API，不衡量模型解题能力。
2. **真实缺陷修复**：复用已冻结的 6 个 Flask/SymPy SWE-bench Lite 问题，各执行关闭压缩、默认 200K 压缩两组，共计划 12 次。模型独立调查、修改和测试。
3. **真实 Worker 调度试跑**：在同一个 SymPy 维护工作负载上比较并发度 1、2。通用 Worker 自行领取共享 Todo，父运行器不指定 item ID。

真实任务的成功需要同时满足：非空生产代码补丁、独立回归测试通过、Agent 正常完成、无执行异常。模型声称完成、只通过自写测试或中断后留下部分正确补丁，都不计为完整成功。

每个真实缺陷尝试最多 40 轮、420 秒；这些是**评测预算**，没有给产品重新添加默认轮数限制。超过预算的失败保留在分母里，同时与完成后测试失败区分。

数据目录：`eval_results/readiness-20261025/`。

## 2. 可靠性结果：7 个场景，各 20 轮

| 场景 | 通过 / 尝试 | 验收内容 |
| --- | ---: | --- |
| 工具派发后 Provider 断流，再恢复会话 | 20 / 20 | 错误被报告，工具结果没有丢失；恢复前后及持久化历史配对完整，后续查询完成 |
| 子进程非正常退出，再恢复会话 | 20 / 20 | 进程提交 tool_use 后直接 `os._exit(23)`，未关闭连接；新 Agent 修复孤立调用并继续查询 |
| 8 个操作系统进程同时抢同一 Todo | 20 / 20 | Barrier 同步起跑，各自持有 SQLite 连接，每轮恰好一个成功领取者，无数据库异常 |
| 租约到期、拒绝旧 Worker 写入、由新 Worker 完成 | 0 / 20 | 旧写入被拒绝，但之后同一连接上的合法更新因残留事务失败 |
| 两个 Worktree 同时提交不重叠修改 | 20 / 20 | 两份修改均合并，父仓库干净，子 Worktree 回收 |
| 两个 Worktree 同时提交相同行冲突 | 20 / 20 | 一个合并、另一个阻断；父文件保持完整版本，无残留 merge/rebase 状态，子 Worktree 回收 |
| 消息投递后、ACK 前消费者重启 | 0 / 20 | 队列消息可持久化，但已投递且未 ACK 的消息不会被领取接口重投 |

共 140 次场景执行，100 次通过、40 次失败。不能把其中通过的场景抽出来宣称“整体故障恢复率 100%”。

并发认领共发生 **160 次进程级领取尝试**，20 轮均只有一个领取者。这不是“160 个 LLM Agent”的吞吐量数据。

崩溃用例验证的是“提交 tool_use 之后、tool_result 之前的进程退出”，不覆盖断电、磁盘故障、外部副作用的 exactly-once。恢复查询使用确定性 Provider，因此 `resume_ms` 不能当成真实模型任务恢复时延 SLA。

租约用例使用真实经过的 50ms 短租约，没有直接修改时间戳；它是加速故障注入，不代表生产默认租约。Worktree 用例验证同一管理器内的并发集成，不代表跨管理器/跨进程合并锁，也不构成安全沙箱。

### 2.1 明确发现：拒绝旧消息后残留 SQLite 事务

复现顺序：

1. 旧 Worker 的任务和运行租约过期。
2. 新 Worker 领取该任务。
3. 旧 Worker 更新 Todo 被拒绝，更新 orphaned run 被拒绝。
4. `append_agent_message(..., owner_id=old_owner)` 的条件 INSERT 没插入记录，抛出 `ValueError`。
5. 新 Worker 在同一 store 上合法完成 Todo，报 `sqlite3.OperationalError: cannot start a transaction within a transaction`。

根因是消息写入错误分支在 commit 前抛错，而借用连接的上下文只释放连接，没有回滚这个隐式事务。Fencing 并非完全失效：旧状态确实没有写进去；缺口在**拒绝后的事务清理和后续可用性**。

建议修复范围：消息写入统一使用有回滚保证的事务边界，并增加“拒绝旧写入之后，合法写入仍可成功”的回归测试。应在修改后重跑同一协议，不能覆盖本轮失败记录。

### 2.2 明确发现：Mailbox 没有未 ACK 消息重投

`claim_agent_messages_for_parent()` 将消息从 queued 改为 delivered，后续只查询 queued。消费者重启后，未 ACK 的 delivered 消息仍在数据库里，但不会通过这个接口再次投递。

这里通过关闭/重开存储连接模拟消费者重建，测量的是存储接口的重投能力，不是另一个真实进程崩溃实验。完整子结果可能仍可从 run 记录手工读取；缺口是消息不会通过当前消费通道自动重投，不等于数据库中的全部结果被删除。

因此，这轮只证明“queued 消息能持久化”，不能声称端到端 at-least-once，更不能声称 exactly-once。管理器还存在先 ACK、后交付上下文的窗口，不能只增加一个重新领取入口就宣称解决所有消息丢失窗口。

建议修复范围：设计投递租约/可恢复游标、幂等消费，以及持久化上下文与 ACK 的一致性边界；明确模型消费前后、工具副作用前后的不同保证。

## 3. 真实模型任务：验收方式

模型为本地配置的 `gpt-5.6-luna`，启动前端点探测返回 READY，且存在非零输入 Usage。

固定任务为 Flask 4992、5063，以及 SymPy 17022、18087、18532、19007。没有按这轮模型结果挑选任务；复用既有固定清单和已准备的源码/环境缓存。

每次尝试保存请求上下文、工具事件、Usage、候选补丁和测试结果。验收在独立干净 checkout 中应用**生产代码补丁**及预置回归测试，模型对测试文件或测试配置的修改不参与独立评分。测试完整性仍取决于所选回归集合，不等于仓库全量测试。

这是 Windows 原生环境下的 SWE-bench Lite 本地子集，不是官方 Docker 榜单成绩。两组各 6 次、每题每组仅 1 次，不能把随机解题差异归因为压缩收益，也不宜给出普遍成功率结论。

已观察到的失败示例：Flask 5063 的模型补丁增加了 Domain 列，自行验证后宣布完成；独立用例要求 Host/Subdomain 列，结果为 55 项通过、2 项失败。这说明“工具正常执行”和“模型说完成”都不足以作为任务验收。

默认压缩若未触发，不能把输入 Token 差异描述为压缩效果。历史受控负载的 41.1% 也不能替换为本轮真实任务的普遍收益。

## 4. Worker 对照试跑的边界

复用既有经参考补丁验收的 4 问题 SymPy 移植组合，作为**一个衍生维护工作负载**，不是 4 个独立 SWE-bench 样本。两组任务、模型、工具相同，都使用私有上下文、共享 Todo 和隔离 Worktree。

并发度 1 按顺序启动 Worker，并发度 2 分波启动两个 Worker；每个 Worker 都通过 `todo_claim` 自行选择 ready task。运行器不分发具体任务，也不代替模型完成代码修改。

每组固定 420 秒墙钟预算，最多每个 Worker 40 轮；每组只试跑一次，固定先 1 后 2，且与其他评测共享机器和 API。记录请求重叠峰值、完整子结果、最终 Todo、合并补丁和独立测试。

这可以检查真实模型 Worker 链路与并发行为，**不能等同于自然单 Agent 与完整多 Agent 产品的公平性能比较**。只有两组都达到相同质量、重复多轮并控制任务与缓存顺序后，才有资格比较加速比。

## 5. 可复现入口

以下命令在项目根目录执行。使用新的输出目录，避免覆盖原始证据。真实模型命令会消耗 API 额度，且依赖已准备的评测缓存。

```powershell
uv run python -m evals.performance.reliability --output eval_results/readiness-rerun/reliability-final --repetitions 20
uv run python -m evals.performance.live_readiness --selection eval_results/context-efficiency/repository-real-v1/selection.json --output eval_results/readiness-rerun/real-issues --parallel 3 --max-turns 40 --timeout-seconds 420
uv run python -m evals.performance.worker_comparison --composite eval_results/context-efficiency/repository-session/selection.json --source eval_results/context-efficiency/repository-ab/selection.json --output eval_results/readiness-rerun/worker-pilot --timeout-seconds 420
uv run python -m evals.performance.evidence_report --root eval_results/readiness-rerun
uv run pytest
```

可靠性命令在存在失败时返回退出码 1；这是明确的失败报告，不是丢失输出。`evidence_report` 要求三组实验均结束，拒绝把未完成的评测汇总成最终报告。

`reliability-smoke`、`reliability-20` 是评测脚本开发阶段输出，其中包含脚本字段错误/中断，**不计入正式数据**。正式可靠性数据只来自 `reliability-final/results.json`，每轮错误和试验环境均保留。

## 6. 简历使用原则

目前可以突出“可恢复 Coding Agent Harness”和任务执行治理，再用进程级认领、会话恢复、Git 冲突阻断数据支撑具体能力。

不要写“生产环境恢复成功率 100%”“多 Agent 提速 X 倍”“真实编码任务节省 41.1% Token”“全仓库 Ruff 全通过”。离线组件通过、真实任务成功、计费减少是不同口径。

较稳妥的一条技术亮点是：

> 构建支持持久化任务规划与隔离 Worker 的 Coding Agent Harness；通过真实 SQLite/Git 故障注入验证任务独占与恢复，在 8 进程、20 轮竞争认领中均保证单领取者，并完成 20 轮非正常进程退出后的会话修复及 20 轮并发代码冲突阻断验证。

这句话描述的是明确测试条件下的实现证据，不是对任意故障、任意代码任务的成功保证。

## 8. 已完成的真实模型结果

12 次缺陷修复、两个 Worker 试跑均已结束，最终机器可读汇总为 `eval_results/readiness-20261025/evidence.json`。

### 8.1 固定真实缺陷：每组 6 次

| 指标 | 关闭压缩 | 默认 200K 压缩 |
| --- | ---: | ---: |
| 完整任务成功 | 1 / 6 | 1 / 6 |
| 仅独立补丁验收通过，含未正常终结的尝试 | 1 / 6 | 3 / 6 |
| 正常结束但独立测试失败 | 2 | 2 |
| 触及 40 轮上限 | 2 | 2 |
| 触及时长预算 | 1 | 1 |
| 捕获的模型 stream 调用 | 208 | 218 |
| 派发工具调用 / 观测到的工具错误 | 253 / 25 | 247 / 25 |
| 请求历史配对违规 | 0 | 0 |
| Usage 完整的尝试 | 5 / 6 | 6 / 6 |
| 实际触发压缩的尝试 | 0 | 0 |

完整成功的两次分别是关闭压缩组 SymPy 18532、默认组 Flask 4992。默认组另有 SymPy 17022、18532 的提交通过独立验收，但 Agent 触及轮次上限，按预设标准仍记为失败。

因此，本轮严格完成率为 **2 / 12**。这不是“系统对任意编码任务只有这个成功率”的总体估计，也不能忽略固定预算和具体模型的影响；但它足以否定“现有单测全部通过，所以真实任务已经稳定生产可用”的推断。

两组观测输入分别为 4,705,335、4,989,003 Token，含缓存读取；前者有一个尝试 Usage 不完整，数值并非完整账单。两组均未触发压缩，**不能据此计算压缩收益**。工具返回错误可能来自测试失败、模糊 edit 匹配等正常反馈，不能把这 50 次错误全部归为运行时 Bug，也不能把未观测错误的调用直接记作工具成功率。

### 8.2 真实通用 Worker 调度试跑

| 指标 | 并发度 1 | 并发度 2 |
| --- | ---: | ---: |
| 观测墙钟时间，含取消收尾 | 421.33 秒 | 421.23 秒 |
| 模型 stream 调用数 | 39 | 62 |
| 重叠模型请求峰值 | 1 | 2 |
| 持久化 Worker 状态 | cancelled × 1 | completed × 1，cancelled × 1 |
| 最终 Todo 状态 | pending × 4 | completed × 1，pending × 3 |
| 独立 FAIL_TO_PASS 目标通过数 | 0 / 5 | 1 / 5 |
| 整个维护任务成功 | 否，超时 | 否，超时 |

并发组确实发生真实模型调用重叠，并完成了一个共享 Todo；但没有在相同质量下完成整个任务，所以**不计算加速比**。FAIL_TO_PASS 数量是用例数量，不是已修复问题数量。

两个组均在取消时存在未获得完整 Usage 的请求，不能据其已捕获 Token 量推导完整计费。并发波次的 `gather` 超时还会使 `worker-results.json` 缺少已经完成的成员；汇总器额外以只读方式查询 SQLite 的 `agent_runs`、`todo_items`，保留这部分真实进展，没有把空返回列表当成“从未完成过任何 Worker”。

### 8.3 下一阶段应优先解决什么

1. 修复拒绝旧消息后的事务回滚，重跑原 20 轮序列，保留本轮失败基线。
2. 完成 Mailbox 的投递恢复与幂等消费协议，并测试 ACK 前/后、上下文写入前/后的崩溃窗口。
3. 针对 4 次轮数耗尽、2 次时间耗尽，分析测试范围、重复工具反馈与收尾策略；另设更高预算诊断组，不能回写本轮分数。
4. Worker 调度器逐个持久化已完成成员的结果，不等整个波次全部返回；增加任务完成质量验收与失败任务调度策略。
5. 在两组都能达到相同验收质量后，扩大真实任务与随机化重复；上下文实验另选自然超过预算的长会话，验证实际触发及完整 Token 成本。

结论：运行时已有可验证的独占认领、历史修复、隔离集成能力，但消息一致性和真实长任务完成稳定性仍有明确缺口；这轮数据支持具体工程能力陈述，不支持“已全面达到生产级”的表述。
