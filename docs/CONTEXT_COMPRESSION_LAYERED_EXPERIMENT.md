## 实验流程

1. 每次运行创建独立临时工作区，启用真实 Read/Write/Snip 工具和真实模型。
2. 同一会话连续读取 12 次观测文件。第 2–8 阶段陆续引入七项约束，第 9–10 阶段修改部分旧约束；模型每阶段输出累积 JSON 状态。
3. L1 每次返回 56,000 字符；其余场景每次返回 16,000 字符，避开 L1 阈值。
4. L2 第 6 阶段显式请求裁剪三个过期读取 ID，保留阶段决策文本。
5. L3 第 9 阶段将上次调用时间设为 3,601 秒之前，保持生产的 3,600 秒阈值。
6. 最终 L4 使用 24,000 Token 的加速预算触发摘要；对照关闭文件恢复与开启恢复。第 6 阶段另读一个小型契约文件，在最终实现时检查它的精确值是否仍可获得。
7. 最后模型写出报价函数和状态回执。独立 Python 子进程检查普通计算、上限、罚值、精度、零下限、负值拒绝、重试次数限制，以及精确状态和源文件值。
8. 改变 seed 后重复三次，按 seed 轮换方案顺序；记录完整 Usage、摘要内容、请求哈希、错误和工具配对校验。失败样本保留在结果里。

## 此次发现和修复

- Snip 未进入 SDK 工具池；补齐实例绑定，在有裁剪请求时无需等待预算超限。
- L3 计时器未接入模型调用；结果缺少工具名且调用 ID 是随机值。改为按历史 tool_use 的 ID 解析真实工具名，并逐个处理并发结果块。
- 裁剪和固定边界摘要可能拆散工具调用与结果；改为成对裁剪、扩展保留边界。
- 压缩之前只在顶层用户请求开始检查；改为每次模型请求前检查，覆盖单条长任务内的工具循环。
- L4 释放量忽略了保留消息；改为按前后上下文实际本地大小计算。摘要失败、空输出和截断时保留原上下文并显式报错。
- 实测发现固定三条消息的后缀会丢弃刚完成的决策，摘要可能漏项；改为原样保留上一轮完整用户交互和当前轮，恢复注入消息不算作新用户轮次。最终加速预算从 18K 调整到 24K，以容纳保留窗口并减少频繁摘要；所有 L4 方案重新配对测试。
- L4.5 重复注入仍保留的文件；加入当前文件内容比对，避免重复恢复，文件内容已变化时仍恢复最新版本。子 Agent 不共享父 Snip 删除队列。
- 完整近期窗口会把摘要标记推到最后五条消息之前；恢复层改为识别当前完整压缩上下文，避免有摘要却跳过恢复。保持相同基线与窗口配置，单独重跑恢复方案。
- 摘要模型可能继续执行历史阶段指令；增加独立的当前摘要请求，让模型把历史指令作为数据处理。实验也明确状态对象只包含 CONFIG_UPDATE 引入的键，辅助文件元数据存放在状态对象之外；L4 基线和实验组均重新运行。

## 数据解释边界

这些结果证明各层在指定工作负载下实际运行，以及此任务的状态保留和代码正确性。它们不代表任意代码库的节省率或生产任务成功率。

- 这是受控的合成编程任务，尚未形成真实仓库问题的 SWE-bench 数据。
- 每组只有三次；均值、标准差和最小/最大值保存在 JSON，不能据此给出生产 SLA。
- L2 的删除候选由实验提供，没有验证模型自主挑选删除内容的质量。
- L3 模拟了空闲时间条件，没有实等一小时，未验证实际缓存 TTL 或过期账单。
- L4 使用加速预算；没有声称跑满默认 200K 窗口或触发全部层的同一轮压缩。
- 主要指标来自中转返回的 Provider Usage，未调用静默回退的 count_tokens 方法来冒充精确计数；本地估算仅作为诊断字段。
- 之前的 35.646% 来自不同的八阶段 L1 工作负载，不能与本次百分比直接比较。
