# Carbide 长任务收尾：失败诊断、预算感知与真实模型对照

日期：2026-10-25。本轮接续可靠性修复，分析真实编码任务中的轮数耗尽、超时和不正确收尾。目标是改善有明确预算的执行，不是提高显示分数或重新加入默认轮数上限。

## 1. 原始证据与原因边界

历史数据保持不变：`eval_results/readiness-20261025/real-issues/report.json`，12 次尝试严格成功 2 次；4 次达到 40 轮，2 次超时，另有 4 次正常结束但独立测试失败。

本轮将每次调用、重复工具签名、无变化 edit、最后调用和预算事件提取为 `eval_results/completion-study-20261025/study/baseline-diagnostics.json`。重复测试可能是必要的修复验证，工具返回错误也可能是正常失败反馈，不一概归为运行时 Bug。

可确认的现象：

- SymPy 17022、18532 的默认压缩组均耗尽 40 轮，但最终生产补丁通过独立回归验收；最后调用仍是 read 或 bash，没有最终回答。原运行时并不告诉模型剩余调用数。
- SymPy 18087 两组均触及 420 秒，发生多次整文件测试，默认组最后还启动了整个 `sympy/simplify/tests`。这支持改进测试范围与时间预算意识，但不能断言所有耗时都来自测试；模型请求、调查和修改同样消耗时间。
- Flask 4992 存在 `old_text == new_text` 的无变化编辑；SymPy 18532 还出现反复缩小读取范围才拿到首行的情况。后者的 read schema 原本已注明 offset 从 0 开始，不能直接认定工具读错文件。
- Flask 5063 等任务正常结束后仍有独立测试失败，涉及需求/API 解释和补丁正确性。增加预算提醒不能替代语义验收。

上述是观察与机制分析，不是对某个单因素的因果效果估计。尤其不能把“补丁验收通过、任务未正常结束”改记为严格成功。

## 2. 实现改动

### 2.1 可选预算的少量提醒

新增 `src/carbide/engine/budget.py`。QueryLoop 仅对调用方明确设置的预算生成提醒：剩余模型调用数跨越 5、1 次，或传入截止时间后剩余时间跨越 60、15 秒。每个维度最多两次，同一边界合并通知。

- `max_turns=None` 仍然是默认行为；没有期限或轮数预算的普通查询不会新增提醒，也没有新增硬上限。
- 剩余次数包含即将发起的调用。提醒要求预留一次调用输出最终结果，优先有针对性的验证，减少可选探索和无法在预算内完成的大范围测试。
- 提醒明确禁止跳过必要检查、掩盖失败或为结束而声称成功。达到原有限制后仍返回 `max_turns`，不额外偷加一轮，也不自动把 Todo 完成当成整个任务成功。
- 提醒在模型请求边界追加到 messages 并持久化，不重建 system、不变更工具 schema；只有消息尾部出现新内容。CLI 输出简短的剩余预算。
- SDK `Agent.query(..., deadline=...)` 接受 `asyncio.get_running_loop().time()` 时钟上的截止时间作为规划提示。宿主仍须使用 `asyncio.timeout()` 等机制执行硬超时；提示本身不会中断正在运行的工具或增加预算。
- `enable_budget_notices=False` 可关闭提醒，用于对照或集成方自有策略。

### 2.2 普通消息的失败事务回滚

预算上下文写入故障注入发现，原普通 `append_message()` 与上一阶段的 mailbox INSERT 有同类风险：存储异常可留下隐式事务。现改用显式事务并回滚。测试检查异常可见、未提交的上下文不进入模型、连接还能继续事务操作。

### 2.3 Worker 评测逐个收集结果

生产管理器原本已将每个 Worker 的结果写入 SQLite；缺口在评测运行器等待整波 `gather()` 后才生成 `worker-results.json`。本轮改为每个成员完成即写出，其他成员超时或被取消时，已完成记录仍保留。

这不是父 Agent 分配任务，Worker 仍然从共享 Todo 自主认领；也不是新增分布式调度器或自动重试策略。

## 4. 真实模型实验协议

模型：`gpt-5.6-luna`。端点在启动前返回 READY，记录于 `eval_results/completion-study-20261025/endpoint-probe.json`。

从已知失败中有目的地选择 3 个诊断案例：SymPy 17022、18087、18532。它们不是随机样本，不代表整体编码成功率；也不是压缩收益实验。

| 组别 | 模型调用上限 | 硬超时 | 预算提醒 | 目的 |
| --- | ---: | ---: | --- | --- |
| control | 40 | 420 秒 | 关 | 同源码下的预算盲对照 |
| guided | 40 | 420 秒 | 开 | 在相同预算下检查提醒是否改善收尾 |
| extended | 80 | 840 秒 | 关 | 单独判断增加预算能否解决问题，不与前两组混算 |

共 9 次，3 个案例并行、同案例各组按固定随机种子打乱顺序，每格仅一次；所有组都使用默认 200K 压缩、相同任务提示、工具和独立验收。没有向模型提供参考补丁或隐藏回归测试。运行前冻结配置、运行时及评测脚本哈希；运行中不改源码，不根据结果追加有利样本。模型调用、工具事件、补丁、独立验收及失败均保存。

严格成功仍要求：非空生产补丁、独立回归通过、正常 completed 且无执行异常。修改测试文件、自报完成、只通过自写测试或触及预算后留下正确补丁均不直接记成功。Usage 不完整的尝试保留，但不能用于完整计费比较。

协议与过程数据位于 `eval_results/completion-study-20261025/study/`。9 次尝试均已终结，`report.json` 标记为 complete。complete 指实验执行结束，不表示 9 次任务成功；失败记录、错误响应和独立验收均保留。

## 5. 真实模型最终结果

| 案例 | 原预算无提醒 control | 同预算提醒 guided | 提高预算 extended |
| --- | --- | --- | --- |
| SymPy 17022 | 40 次调用，max_turns；补丁验收通过，严格失败 | 11 次调用，中转 503；失败，提醒尚未触发 | 61 次调用，正常完成，独立验收通过 |
| SymPy 18087 | 12 次调用，中转 503；失败 | 36 次调用，正常完成；独立 `test_Factors` 失败 | 54 次调用，正常完成；独立 `test_Factors` 失败 |
| SymPy 18532 | 30 次调用，正常完成，独立验收通过 | 29 次调用，正常完成，独立验收通过；未触发提醒 | 35 次调用，正常完成，独立验收通过 |
| **严格成功 / 尝试** | **1/3** | **1/3** | **2/3** |

观测到 308 次模型 stream 调用，请求历史配对违规为 0；本轮 9 次均未触发上下文压缩。7 次尝试 Usage 完整，另 2 次因中转错误中断请求而不完整。无法据此比较完整账单，更不能计算本轮压缩收益。

最终两次尝试出现的实际错误为 HTTP 503，`model_not_found`，消息包含 `No available channel for model gpt-5.6-luna`。这是当时中转没有可用模型通道的响应，不是证明 query loop 崩溃或工具错误。它们保留在 control/guided 各自的分母，不删样本、不补跑覆盖原记录。启动时 READY 只证明当时可用，不保证后续整场服务稳定。

运行时源码 SHA-256 在实验前后均为 `384be6077e73c940c71bc7486b30771a7632d1a281d7a494effa10002dad0945`。所有尝试的共用 repository harness 哈希相同，具体值由每次 result.json 的 `harness_sha256` 保存。没有在实验中途根据结果调整策略。

### 能得出的结论

1. **不能证明预算提醒提高了正确完成率。** guided 的严格成功是 1/3，与 control 相同；唯一严格成功的 guided 尝试没有触发提醒。18087 在第 36 次调用前收到“剩余 5 次”提醒，随后正常结束，但补丁仍不正确。17022 guided 在提醒触发前被中转故障打断，缺少可用的同预算对照结果。
2. **预算大小确实需要单独诊断。** 17022 control 的补丁已经通过验收但未收尾；extended 的独立尝试在第 61 次调用正常完成并通过验收。这提供了预算不足的具体案例，但两次是独立随机运行，不能声称原轨迹只要多 21 轮必然成功，也不把不同预算的 1/3、2/3 写成产品成功率提升。
3. **补丁质量是另一个独立瓶颈。** 18087 guided 和 extended 都修改了 `sympy/simplify/fu.py`，目标 `test_fu` 通过、`test_Factors` 失败；正常输出最终回答、增加预算均不足以补齐底层语义。原有 PASS_TO_PASS 用例没有失败，也不代表新增目标已满足。
4. **Worker 结果保留缺口已由回归测试覆盖，但没有新加速比。** 本轮只修正评测逐个收集结果，不另跑一个不足以公平比较速度的小样本。

本轮结果不与历史 2/12 合并成一个更有利分数：任务选择、运行时和预算条件均不同。预算提醒属于已验证其边界与一致性的规划能力，尚无可用于简历的真实成功率提升数据。

### 后续优先级

- 为真实任务定义可检查的需求清单与有针对性的复现，尤其追踪“局部高层用例通过，但相关底层行为仍失败”；不要向 Agent 泄露隐藏验收补丁，也不要把模型自写测试作为唯一成功依据。
- 中转恢复后，在新协议、新目录中补足同预算随机化重复；当前故障样本保持不变。先确认提醒有实际触发样本，再评估正确完成率、收尾率和成本，而非只看 completed。
- 如果要建立默认生产预算，需基于更多任务的调用/时长分布确定；不能直接把本轮 80 轮、840 秒当作产品默认值。

```powershell
uv run python -m evals.performance.completion_study --selection eval_results/readiness-20261025/real-issues/selection.json --baseline eval_results/readiness-20261025/real-issues/report.json --output eval_results/completion-study-rerun/study
```
